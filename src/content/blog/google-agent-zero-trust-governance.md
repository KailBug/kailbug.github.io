# 把模型当作可能被攻陷的内部人：拆解 Google 的 Agent Zero Trust / Agent Governance 架构

> Agent 真正进入生产，不是因为它更会说话，而是因为它开始拥有身份、调用工具、执行代码并修改业务状态。也正是在这一刻，传统的“给模型写一段安全提示词”彻底失效。Google 给出的答案并非一个单独产品，而是一套从单次执行到企业级 Agent 舰队的纵深防御体系：底层以身份、隔离、签名和网络边界建立硬约束，上层以注册中心、语义策略、内容检查、可观测性与威胁检测形成治理闭环。

本文基于 Google Cloud、Google Developers、Google Security 与开源参考实现截至 2026 年 8 月公开的材料，试图回答三个问题：这套架构究竟在防什么；每一层怎样配合而不是彼此替代；以及，一个不一定运行在 Google Cloud 上的现代 Agent Harness，能从中借鉴什么。

## 一、Agent 的安全问题，已经不是“输出是否合规”

聊天模型主要产生文本，最坏结果通常是错误、冒犯或泄密；Agent 则会把模型生成的计划转化成 API 请求、数据库写入、邮件发送、代码执行、支付与云资源变更。风险因此从“生成了什么”扩展为“改变了什么”。一个被间接提示注入污染的客服 Agent，可能在读到恶意工单后调用退款接口；一个编程 Agent，可能把网页里的隐藏指令当作任务的一部分，读取环境变量并向外发送；一个多 Agent 系统中，上游 Agent 的错误还可能通过 A2A 委派被放大成跨系统级联故障。

这也是为什么系统提示词不能充当安全边界。提示词和模型输出都处在概率系统内部：它们会被上下文污染，行为会随模型升级、提示调整和工具描述变化而漂移，也无法提供密码学意义上的身份、完整性和不可抵赖性。Google 的 Zero Trust 假设更接近传统安全工程：**模型可能被诱骗，Agent 进程可能被攻陷，凭证可能被窃取，工具返回的数据可能带毒，因此每一次访问和每一次高风险动作都必须在模型上下文之外重新验证。** Google 对 Agent 安全的早期总结是三个原则——人类控制者必须明确、Agent 权力必须受限、Agent 的计划与动作必须可观察；其防御方法则刻意混合确定性控制与基于推理的动态控制，而不是相信其中任何一类可以单独解决问题。[Google Cloud：How Google secures AI Agents][google-secure-agents]

从工程上看，这里至少存在六类互不等价的风险：用户输入和检索内容可能携带直接或间接提示注入；Agent 身份或用户委托关系可能被伪造；模型可能提出越权、越界或与原始意图不一致的工具调用；动态生成的代码可能逃逸、探测宿主机或外传秘密；已获授权的进程仍可能篡改业务数据；最后，即使单次调用全部“合法”，连续调用组合起来也可能形成数据外传、资源耗尽或权限升级路径。Agent Governance 的价值，就是让这些风险分别落到可以执行、可以审计的控制点上。

## 二、运行时 Zero Trust 与舰队级 Governance

Google 近期材料中有两种容易被分开阅读的叙事。第一种来自 ADK 的 `zero-trust-agents` 参考实现，它以客服退款为例，把防线归纳为三根支柱：对每次状态写入做密码学签名，在 gVisor 沙箱中执行不可信代码，在模型与工具前后设置确定性的语义网关。[Google Developers：Build zero-trust AI agents][google-zero-trust-blog] 第二种来自 Gemini Enterprise Agent Platform，将企业治理描述为以 Agent Identity、Agent Registry、Agent Gateway 为主轴，再叠加 Model Armor、Semantic Governance、Agent Anomaly Detection、Agent Threat Detection 和统一安全视图的治理栈。[Gemini Enterprise Agent Platform 概览][agent-platform-overview]

两者并不矛盾。前者回答“某次执行怎样不越狱、不越权、不留下无法追责的写入”，后者回答“数百个团队、数千个 Agent 和工具怎样被发现、授权、持续监测和统一处置”。把它们合在一起，才能看到完整的信任链。

![azt-01](/img/azt1.png)

这张图里最重要的不是产品名称，而是两个架构事实。第一，Agent Gateway 必须成为工具调用的**必经之路**，否则绕过网关的直连凭证会让治理形同虚设。第二，控制面负责定义身份、资产、策略和风险，数据面则在每次调用发生时执行检查；只建设控制台而没有不可绕过的执行点，得到的只是资产报表，不是 Zero Trust。

## 三、身份不是一个服务账号，而是一条可验证的委托链

传统微服务常用一个服务账号代表整个工作负载，但 Agent 的归责问题更复杂。同一个 Runtime 中可能运行多个 Agent；同一个 Agent 既可能自主处理后台任务，也可能代表某位用户访问 Gmail、Drive 或财务系统。如果它们共享进程级凭证，日志最多只能说明“这个容器调用过接口”，无法说明是哪一个 Agent、受哪位用户委托、基于哪次会话和哪条策略完成了动作。

Google 的 Agent Identity 因而被设计成独立于人类身份和通用服务账号的一等主体。当前实现基于 SPIFFE 风格的信任域和不可变资源路径，为 Agent 自动配置同一身份对应的 X.509 证书；Context-Aware Access 默认使用 mTLS 绑定的、证书约束的令牌，使偷出运行环境的访问令牌难以在别处重放。[Agent Identity 文档][agent-identity] Agent Gateway 再以这个身份作为授权主体，通过 IAP、IAM Allow/Deny 和上下文信号决定它能否访问某个 Agent、MCP Server、工具或方法。[Agent Gateway 文档][agent-gateway]

但“Agent 是谁”只解决了一半问题。对于代表用户执行的 workforce agent，还必须保留“谁让它做”的用户身份；对于自主运行的 workload agent，则必须有明确的服务所有者、任务来源和授权边界。理想的审计主体不是单个字符串，而是复合上下文：用户主体、Agent 主体、Agent 版本、会话或运行 ID、委托链、当前目标、策略版本和审批证据。Google 的文档也明确指出，在用户委托流中，日志应同时显示用户身份和 Agent 身份。这样做的结果不是把 Agent 假装成人，而是避免两种危险的归责坍缩：既不能让用户权限被一个拥有更大固有权限的 Agent 放大，也不能让所有动作都匿名归到一个共享机器人账号。

真正的最小权限还应当是短时、按任务和按工具生效的。一个“能访问采购系统”的静态角色仍然过宽；更好的表达是：这个采购 Agent 在本次经过授权的会话中，可以读取供应商目录，可以创建不超过某一额度的草稿订单，但不能提交付款，不能访问工资数据，授权在任务结束后自动失效。Google 的 Principal Access Boundary 用来给主体设置无论继承何种角色都不能越过的资源上界；VPC Service Controls 则从目标资源与数据移动方向上增加另一道边界。二者说明了一个关键区别：IAM 主要回答“谁可以做什么”，网络和数据边界还要回答“数据可以去哪里”。[Google Cloud：VPC Service Controls for agentic AI][vpc-sc-agents]

## 四、密码学签名解决的是完整性与归责，不是业务正确性

在 Google 的退款 Agent 参考实现中，每个状态变更都由特定 Agent 的密钥签名，数据库入口守卫在提交事务前验证签名，后台审计任务则持续扫描账本。一旦有人把 149 美元的退款直接改成 10,000 美元，原签名就不再匹配。生产映射使用 Cloud KMS 与 Cloud HSM，让私钥不离开受保护硬件，Agent 仅获得调用特定签名密钥的权限；本地演示为了零依赖才以 HMAC 模拟。[开源参考实现][zero-trust-repo]

这层控制很容易被过度解读。签名能够证明“持有某个 Agent 身份的执行体确实对这一份规范化载荷签过名，载荷随后没有被悄悄改掉”，却不能证明退款本身符合业务规则。一个被提示注入劫持、但仍合法持有密钥的 Agent，同样可以签下一笔恶意交易。因此签名载荷至少应覆盖 Agent ID、代表的用户、动作类型、目标资源、关键参数、时间戳、随机数或幂等键、运行 ID、策略判定版本与审批引用；在它之前仍要有授权、金额上限、状态机约束与必要的人类审批。

这也揭示了三类经常混在一起的保证：认证证明调用者是谁，授权判断它是否有资格做这类事，完整性证明提交内容没有被替换。Agent Harness 必须同时具备三者。只做 JWT 认证无法阻止合法身份做错事，只做语义审核无法防止数据库中的事后篡改，只做审计日志则只能在损失发生后解释现场。

## 五、把所有动态代码当作恶意样本运行

Agent 生成代码后直接调用 `exec()`，或者在与业务服务同权限的普通容器中执行，是最危险也最常见的捷径之一。普通容器仍与宿主共享内核；即便没有逃逸漏洞，挂载目录、环境变量、云元数据服务、默认网络出口和过高的 Linux capabilities 也足以造成秘密泄漏。Google 的参考方案使用 gVisor 的用户态内核拦截系统调用，并同时关闭网络、丢弃全部 capabilities、只读挂载代码、限制 CPU 和内存、设置硬超时。[Google Developers：gVisor 隔离示例][google-zero-trust-blog]

这里的设计原则比“选 gVisor”更重要：**生成代码不是 Agent 自身可信代码的延伸，而是一件来自不可信供应链的临时制品。** 它应在一次性执行环境中运行，默认无网络、无云凭证、无宿主文件、无持久磁盘，只通过显式挂载获得最小输入，并且把输出当作不可信内容再次检查。如果任务确实需要联网，应让它访问受控的 egress proxy 或声明式下载工具，而不是开放任意 Socket；如果需要修改文件，应使用任务专属工作区和提交阶段，而不是把生产仓库直接以读写方式挂载进去。

隔离也不能只覆盖“代码工具”。浏览器自动化、Shell、SQL、包管理器、MCP 工具和计算机操作都具有不同的副作用，应共享相同的能力模型：读操作与写操作分离，网络目标受限，资源和时间有预算，所有跨边界输出可追踪。Google 的 Governance 文档已允许按 MCP 的 `toolName`、`method` 和 `isReadOnly` 属性做授权，这正是在协议层把工具副作用变成可执行策略，而不是只依赖工具名称猜测风险。[Google Cloud：Agent Gateway 的 MCP 属性授权][agent-gateway]

## 六、Agent Registry 不是应用商店，而是治理的事实源

当组织只有三个 Agent 时，团队还可以靠 README 记住谁调用谁；当规模扩大后，真正的风险来自“没人知道它存在”。Agent Registry 的定位是统一登记自建、Google 和第三方 Agent，以及 MCP Server、工具与外部 Endpoint，并记录版本、框架、能力、工具名称和注解等元数据。[Agent Registry 文档][agent-registry] Gateway 以注册信息解析目的地并实施策略，拓扑视图再利用追踪数据还原 Agent 与 Agent、Agent 与 MCP Server 之间的真实关系。

这让 Registry 同时承担发现与治理，但安全上不能把“已注册”等同于“可信”。一个成熟条目还需要所有者、代码与镜像来源、发布签名、当前版本、数据分级、读写副作用、允许的调用者、可访问目标、审批级别、最近评估结果、漏洞状态、下线时间与紧急联系人。工具描述本身也是安全材料：Semantic Governance 需要依赖准确的工具描述和参数语义来判断调用意图，描述被污染、过时或刻意模糊都会削弱判定。

因此，注册过程必须接入发布流水线，而不是让任何 Agent 自报能力后立即获得信任。镜像、技能包和 MCP Server 先经过来源验证、漏洞扫描、静态检查、红队测试和风险分级，再进入可用目录；运行时只允许连接被批准的版本。Google Agent Gateway 的默认策略是阻止访问本地 Registry 中未注册的远程 MCP Server、Agent 或工具，管理员虽然可以放开这个限制，但那应被视为显式降低安全基线，而不是开发便利项。[Agent Gateway 文档][agent-gateway]

## 七、Gateway 的真正价值：把“模型想做什么”变成一次外部裁决

Agent Gateway 是整套架构的执行中心。它位于 user-to-agent、agent-to-agent 和 agent-to-tool 通信路径上，终止和建立安全连接，解析 HTTP、MCP、A2A 等协议中的身份与属性，并把一次工具调用委托给多种判定器。IAM 与 IAP 检查主体和静态权限，Registry 检查目标与能力是否被批准，Model Armor 检查提示注入、恶意 URL、敏感数据与有害内容，Semantic Governance 则判断调用是否与原始用户意图和组织业务约束一致；自定义 Service Extension 还可以接入企业自己的风控或授权引擎。[Agent Gateway 文档][agent-gateway]

这里必须区分“确定性语义网关”与“概率性语义治理”。Google 的 ADK Zero Trust 演示用正则、参数校验和业务上限构造确定性防火墙，例如退款不得超过订单金额、输出不得包含特定密钥格式，并要求这些规则进入 CI 回归测试。这类规则适合保护金额、资源范围、状态迁移、允许列表、速率与数据类型，因为相同输入应得到相同结论。Agent Platform 的 Semantic Governance 则使用 LLM 在运行时比较原始用户请求、会话历史、拟议工具调用和自然语言约束，能够识别“总结日历”与“发送邮件”之间的意图偏离，也能表达“超过 75 美元的退款不得自动处理”一类动态业务规则。[Semantic Governance 文档][semantic-governance]

后者很强，但 Google 文档明确警告：它本身是生成式 AI 服务，判定具有概率性，可能出错，并建议先以 dry-run 观察结果再启用阻断；截至本文时间，该能力仍为 Preview，且 Semantic Governance Policy 不支持 VPC Service Controls。[Semantic Governance 最佳实践][semantic-best-practices] 因而正确的优先级应是：能用类型、集合、数值、状态机和访问控制表达的硬边界，先用确定性规则执行；无法静态表达的意图一致性和上下文组合，再交给语义判定；任何一个硬拒绝都应终止调用，语义不确定或风险过高则升级人工审批，而不是让另一个模型“投票放行”。

Model Armor 与 Semantic Governance 也不应混为一谈。前者更像内容安全与 AI 防火墙，扫描请求、响应和 Agent 交互中的注入、越狱、恶意 URL、敏感数据与有害内容；后者更像意图门，评估具体工具调用是否符合可信用户意图和业务约束。一个调用可能不含任何恶意文本，却仍然超出用户授权；也可能业务上合理，但参数里夹带敏感数据。两类检查需要同时存在。[Model Armor][model-armor]

## 八、对现代 Agent Harness 工程的借鉴

Google 方案最值得复制的并不是某个云产品，而是它把安全能力放进了 Harness 的控制流。所谓 Agent Harness，不应只是包装模型调用、工具循环和会话状态的 SDK；它应该是 Agent 的微内核，掌握身份、能力发放、策略裁决、隔离执行、状态提交和证据记录。对任何云和任何模型，至少可以落实以下九项工程原则。

**第一，让每个 Agent 和每次运行都有独立身份。** 身份粒度不能停留在进程、集群或 API Key。Harness 应原生携带 `agent_id`、版本、`run_id`、用户委托与父级 Agent 委托，并用短时、受众绑定、不可跨环境重放的凭证调用工具。多 Agent 委派时，子 Agent 不应自动继承父 Agent 的全部能力，而应收到目标明确、范围收窄、可过期的 delegation token。

**第二，工具只能通过一个不可绕过的中介执行。** 工具 SDK 不应把长期密钥交给模型侧进程，也不应允许 Agent 直接拼接 URL。Harness 把模型输出解析为结构化意图，Gateway 或 broker 再解析目的地、获取短时凭证、执行策略并调用工具。对本地文件、Shell 和浏览器等“非 API 工具”，也要经过同一能力代理，而不是成为网关治理的盲区。

**第三，把工具定义升级为安全契约。** 一个可治理的工具 Schema 除了名称和参数，还要声明副作用、读写属性、数据分类、幂等性、可逆性、资源范围、最大成本、所需身份、审批条件和输出信任级别。模型看到的是便于推理的描述，策略引擎读取的是机器可验证的 manifest；两者必须来自同一个版本化事实源，避免自然语言说明和实际权限漂移。

**第四，把规划与提交分成两个阶段。** 模型可以自由地产生计划，但不能因为“计划已经生成”就获得执行权。Harness 先生成 typed action plan，再做权限、业务不变量、语义意图和风险评估；高风险动作展示 diff、影响范围、预计成本和回滚方案后再审批；真正提交时使用幂等键、乐观锁或事务，并对关键写入签名。这个模式类似数据库的 prepare/commit，也让 dry-run、仿真和审计成为自然能力。

**第五，Capability 应按任务即时发放。** 不要在 Agent 启动时把所有工具和凭证放入上下文。先暴露少量只读发现能力，在任务需要时加载被批准的 Skill，再为具体工具发放有范围、有次数、有预算、有过期时间的能力。Google 对 Agent Skills 的治理已经体现这种 progressive disclosure：技能加载、资源读取、脚本运行本身都作为可拦截的工具调用，供应链和上下文膨胀因此可以一起治理。[Google Cloud：Governing Agent Skills][governing-skills]

**第六，把不可信数据的来源标签传播到底。** 用户明确指令、网页内容、邮件正文、RAG 片段、工具返回、长期记忆和其他 Agent 消息不应在 prompt 拼接后失去边界。Harness 需要维护 provenance 与 taint：某段内容来自外部网页，就不能仅凭其中的文字触发发送邮件或上传文件；某条记忆来自未经确认的模型推断，就不能直接成为财务决策事实。策略判断应看到这些标签，而不只是被压平后的对话文本。

**第七，把沙箱、网络和预算视为同一类影响半径控制。** 每次代码或计算机操作使用一次性环境，默认无网络和秘密，CPU、内存、磁盘、Token、工具次数、并发和墙钟时间都有上限。预算耗尽必须触发可解释的暂停或终止，不能由 Agent 自己申请无限续期。这样既防攻击，也防循环规划把下游系统打成内部 DoS。

**第八，让 Trace 成为安全证据，而不只是性能瀑布图。** 每个 span 应能关联模型输入输出摘要、工具调用、身份、策略版本、判定理由、审批、沙箱事件、状态变更签名和最终结果。敏感原文可以脱敏或单独加密，但关联 ID 和不可变事件链必须保留。只有这样，异常检测才能从“这个请求很慢”上升到“这个 Agent 在读取受污染网页后加载了发送工具，并试图向新域名传输高敏数据”。

**第九，把评估与安全回归接进发布门。** 提示、模型、工具描述、策略、依赖和权限任一变化，都可能改变 Agent 的有效行为。Harness 的版本工件应包含场景测试、攻击样本、权限快照、策略测试和预期 Trace；先仿真，再 shadow/dry-run，再金丝雀，最后扩大流量。线上异常和人工驳回应自动进入新的回归集，但不能未经审核直接反向训练或改写策略，以免攻击流量污染治理闭环。

如果把这些原则浓缩成一个跨云的最小参考栈，可以得到如下对应关系：Google 的 Agent Identity 对应 Harness 的 per-agent / per-run 身份与委托链；Agent Registry 对应版本化能力目录与供应链事实源；Agent Gateway 对应唯一工具 broker；IAM、PAB 与 VPC-SC 对应主体权限、资源上界和数据目的地边界；Model Armor 与 Semantic Governance 对应内容检查和意图门；gVisor 与 KMS 对应隔离执行和可验证提交；OpenTelemetry、Anomaly Detection 与 Threat Detection 对应证据、行为基线和联动处置。产品可以替换，这些责任不能消失。


## 结语

Google 这套 Agent Zero Trust / Agent Governance 架构的核心，不是把更多安全提示词塞进模型，也不是简单地在 Agent 前面加一道内容过滤。它真正完成的是一次责任迁移：模型负责在开放问题中推理，基础设施负责定义不可逾越的边界；Agent 可以提出动作，但身份系统、策略引擎、Gateway、沙箱、审批人与资源入口共同决定动作能否发生；行为可以是概率性的，授权、隔离、写入完整性和审计链却必须尽可能确定。

对现代 Agent Harness 而言，最值得借鉴的一句话是：**不要把 Harness 只做成模型的循环调度器，要把它做成自主系统的安全内核。** 当身份随调用传播、工具通过唯一出口、能力按任务发放、代码在隔离域执行、状态变更可验证、策略在模型之外裁决、异常能够即时中断时，Agent 的自主性才不再等同于不可控。Zero Trust 不是压制 Agent 能力，而是让组织敢于把更重要的能力交给它。
